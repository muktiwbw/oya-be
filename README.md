# OYA

A Go task backend with SQLite persistence. This MVP provides one shared workspace with no authentication: every caller can read and update all tasks. Use it locally or on a trusted internal network.

## Prerequisites

- Go 1.25.9 (selected automatically through `go.mod` when toolchain downloads are enabled).
- Make.
- Docker Desktop or a Docker Engine for integration tests and container builds.
- A C compiler for `make test-race`. Production builds use a pure-Go SQLite driver and can use `CGO_ENABLED=0`.

The module path is `oya-be`; change it and local imports together when a remote repository is selected. No mise installation is required.

## Local development

```sh
cp .env.example .env
make help
make test
make run
```

The server listens at `http://localhost:8080`. It creates `./data/oya.db` and applies embedded versioned migrations automatically. A migration failure prevents startup. Database files and build output are ignored by Git.

Apply pending migrations without starting the HTTP server:

```sh
make migrate
OYA_DB_PATH=./data/other.db make migrate
# With a built binary:
./bin/oya migrate
```

The command uses the same environment configuration and embedded migrations as server startup. It creates the database if needed, skips already applied migrations, and exits with a nonzero status on failure. Each pending migration runs in a transaction.

```sh
make check             # formatting, vet, non-containerized tests
make test-race         # race detector
make generate-mocks    # regenerate Mockery mocks after changing task ports
make build            # bin/oya
make integration-test # application and test-runner images, then Testcontainers
```

`make integration-test` runs the test runner in Docker. Testcontainers creates a separate application container with a unique volume, waits on `/readyz`, discovers the mapped port, and cleans up resources. The runner uses the Docker socket and `host.docker.internal` to reach mapped ports. Override `DOCKER_SOCKET` or `TESTCONTAINERS_HOST` when your Docker setup uses a different socket or gateway. Integration tests are tagged and excluded from `go test ./...`.

Unit tests use Testify `require` for prerequisites and `assert` for independent checks. Application dependency mocks are generated by Mockery v3.5.5 using `.mockery.yml`. Run `make generate-mocks` after changing `Repository`, `Clock`, or `PublicIDGenerator`; keep the resulting `internal/task/mocks/mocks.go` in version control and do not edit it manually. Service tests use `package task_test` and import `oya-be/internal/task/mocks`, avoiding an import cycle with the task package. Generated constructors register expectation checks with test cleanup. Tests use typed `EXPECT()` calls and explicit call counts. Production packages must not import the mocks package.

The generation target uses the project's Go toolchain and a pinned `go run` command, so no global Mockery installation is required. The first run may download Mockery dependencies and its template schema. To use a locally installed matching binary, run `make generate-mocks MOCKERY=mockery`. Existing generated mocks let `make test` run without regenerating them.

## Configuration

The application, migration command, and healthcheck load an optional `.env` file from the current working directory. Copy `.env.example` to `.env` and edit your local settings. Process environment variables take precedence over `.env`, then built-in defaults apply. An explicitly empty environment variable overrides the file and is validated normally. Missing `.env` files are allowed; malformed or unreadable files cause startup to fail. Local `.env` files are ignored by Git and excluded from Docker build contexts.

For Docker, pass configuration with `-e` or `--env-file .env`. Set `OYA_DB_PATH=/data/oya.db` when using the image's data volume; the local example uses `./data/oya.db`.

| Variable | Default |
|---|---|
| `OYA_HTTP_ADDR` | `:8080` |
| `OYA_DB_PATH` | `./data/oya.db` (`/data/oya.db` in the image) |
| `OYA_LOG_LEVEL` | `info` (`debug`, `info`, `warn`, or `error`) |
| `OYA_SHUTDOWN_TIMEOUT` | `10s` |
| `OYA_REQUEST_BODY_LIMIT` | `65536` (positive, at most 65536 bytes) |
| `OYA_IDEMPOTENCY_TTL` | `24h` |

HTTP defaults: header read timeout 5 seconds, read timeout 10 seconds, write timeout 15 seconds, idle timeout 60 seconds. SQLite uses one connection, WAL, foreign keys, and a 5-second busy timeout. SIGINT and SIGTERM trigger graceful shutdown; the database closes after requests finish or the shutdown deadline is reached.

## Docker

```sh
make docker-build
docker run --rm --name oya -p 8080:8080 -v oya-data:/data oya:integration
```

The image runs as UID/GID 10001 and stores data on a volume. A host bind mount must be writable by that user. Keep one application instance per SQLite database file. Use a server database adapter before introducing multiple application instances sharing storage.

`GET /healthz` is process liveness without querying the database. The image health check uses it. `GET /readyz` checks database availability after migrations and returns 503 during shutdown. `GET /version` returns build metadata. Set Docker build arguments `VERSION` and `COMMIT` to supply release metadata.

## API examples

See [resources/api/spec.yaml](resources/api/spec.yaml) for the complete API contract.

```sh
curl -i http://localhost:8080/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: create-task-001' \
  -d '{"title":"Prepare release notes"}'
```

Creation returns 201, a `Location` header, and a task with a UUIDv7 `public_id`, status `todo`, description `""`, version 1, and UTC timestamps with three millisecond digits. Internal numeric IDs never appear in API responses. JSON null descriptions and unknown fields are rejected.

Generate one unique idempotency key per intended creation, for example with a client UUIDv4 generator. Retry that operation with the same key and body. A matching retry returns the original create response; changed input with the same key returns 409. Validation failures do not consume the key. After the TTL the key may be reused. Identical content with a fresh key creates a separate task.

```sh
curl 'http://localhost:8080/api/v1/tasks?limit=2&status=todo'
# Resend pagination.next_cursor unchanged with the same status filter:
curl 'http://localhost:8080/api/v1/tasks?limit=2&status=todo&cursor=TOKEN'

curl http://localhost:8080/api/v1/tasks/PUBLIC_ID
curl -X PATCH http://localhost:8080/api/v1/tasks/PUBLIC_ID/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"doing","expected_version":1}'
```

Lists sort by `created_at DESC, public_id ASC`. Pagination is forward only; `next_cursor: null` marks the last page. Changing the status filter requires starting a new traversal. Pages do not provide a snapshot across requests.

All status transitions are allowed. A real status change increments version; a no-op preserves version and timestamp. `expected_version` is required and returns 409 for a stale version, even on a no-op. Timestamps may be equal for two changes within one millisecond; version is the concurrency indicator.

Edit a title and/or Markdown description source with the same required optimistic-concurrency version. An empty description clears it; Markdown is returned as source text and this service does not render or sanitize HTML.

```sh
curl -X PATCH http://localhost:8080/api/v1/tasks/PUBLIC_ID \\
  -H 'Content-Type: application/json' \\
  -d '{"title":"Revised task","description":"## Notes","expected_version":1}'
```

## Backup and restore

Stop the service before copying data. With WAL mode, copy the database directory including any remaining `-wal` and `-shm` files as a consistent set. Keep the backup outside the live data directory. To restore, keep the service stopped, restore the entire saved directory to the mounted data location, ensure UID 10001 can access it, and restart. Do not copy only the main database file while the service is writing.

## Architecture and delivery

`internal/task` owns application behavior and repository ports. HTTP handlers translate requests into service calls. Chi v5 registers method-specific routes in `internal/transport/http/routes.go` on top of Go's standard HTTP server. Task handlers, health handlers, DTO contracts, shared helpers, and middleware live in `task_handler.go`, `health_handler.go`, `task_dto.go`, `health_dto.go`, and `error_dto.go`, `util.go`, and `middleware.go`. Request and response shapes are named DTO structs; encoding, decoding, error mapping, and query parsing are helpers in `util.go`. Domain-to-DTO conversion lives beside the relevant DTO; handlers use `newTaskDTO` from `task_dto.go`. Root middleware supplies request IDs, security headers, and JSON panic recovery; custom routing errors preserve the JSON envelope and 405 `Allow` headers. `internal/persistence/sqlite` owns SQL, transactions, and migrations. `cmd/oya` wires adapters and manages lifecycle. Tests use injected clocks and ID generators. Development documents live in the Git-ignored `.dev/` folder: `.dev/SPECS.md` is the behavior contract and `.dev/TASKS.md` records delivery progress.

SQLite tests live directly in `internal/persistence/sqlite/repository_test.go` and open temporary databases for each scenario. They cover persistence, concurrency, migrations, and query plans. Shared database test infrastructure and PostgreSQL compatibility testing are deferred until needed.
