# OYA

A Go task backend with PostgreSQL persistence. OYA provides user authentication, user-owned boards, and board-scoped task management with optimistic concurrency control, cursor-based pagination, and idempotent creation.

## Prerequisites

- Go 1.26+ (selected automatically through `go.mod` when toolchain downloads are enabled).
- PostgreSQL 16+ (or running via Docker).
- Make.
- Docker Desktop or a Docker Engine for running Flyway migrations, container builds, and integration tests.
- A C compiler if running `make test-race` (production builds use pure Go with `CGO_ENABLED=0`).

The module path is `oya-be`; change it and local imports together when a remote repository is selected. No mise installation is required.

## Local development

```sh
cp .env.example .env
make help
make dev-db            # start PostgreSQL via Docker Compose
make migrate           # apply migrations using Flyway
make test
make run
```

To stop the development database when done:

```sh
make dev-db-stop
```

The server listens at `http://localhost:8080`. It connects to PostgreSQL using `OYA_DATABASE_URL` and validates connection readiness at startup.

### Database Migrations & sqlc

Database schema migrations are versioned Flyway scripts located in `migrations/` (`V<number>__<description>.sql`).

Apply pending migrations using Docker and Flyway:

```sh
make migrate
# Custom database URL or credentials:
FLYWAY_URL=jdbc:postgresql://localhost:5432/my_db FLYWAY_USER=postgres FLYWAY_PASSWORD=postgres make migrate
```

Verify the database connection without starting the HTTP server:

```sh
# With a built binary:
./bin/oya migrate
```

When modifying queries in `queries/` or the database schema, regenerate type-safe Go code with sqlc:

```sh
make sqlc
```

`sqlc` runs through pinned `go run` in the Makefile, so no global installation is required.

### Testing & Code Quality

```sh
make check             # formatting check, vet, and non-containerized tests
make fmt               # format Go source files
make vet               # run go vet
make test              # run unit tests
make test-race         # run unit tests with race detector
make generate-mocks    # regenerate Mockery mocks
make build             # compile bin/oya
make integration-test  # run Testcontainers integration tests in Docker
```

`make integration-test` executes containerized integration tests using Testcontainers. It boots isolated PostgreSQL and application containers, runs Flyway schema migrations, and executes the full end-to-end lifecycle test suite (authentication, board CRUD, task CRUD, idempotency, soft deletion, and cascading deletion).

Unit tests use Testify `require` and `assert`. Application dependency mocks are generated by Mockery v3.5.5 using `.mockery.yml`. Run `make generate-mocks` after changing interface ports (such as `task.Repository`, `board.Repository`, `user.Repository`, `Clock`, or `PublicIDGenerator`).

## Configuration

The application, migration verification, and health check load an optional `.env` file from the current working directory. Copy `.env.example` to `.env` and edit your local settings. Process environment variables take precedence over `.env`, followed by built-in defaults. Missing `.env` files are allowed; malformed or unreadable files cause startup to fail. Local `.env` files are ignored by Git and excluded from Docker build contexts.

| Variable | Default | Description |
|---|---|---|
| `OYA_HTTP_ADDR` | `:8080` | Host and port to listen on (port between 1 and 65535) |
| `OYA_DATABASE_URL` | `postgres://postgres:postgres@localhost:5432/oya?sslmode=disable` | PostgreSQL connection URL |
| `OYA_JWT_SECRET` | `oya-dev-secret-change-in-production-min-32-chars` | Secret key for JWT signing (minimum 16 characters) |
| `OYA_JWT_EXPIRATION` | `24h` | JWT token validity duration (e.g. `24h`, `1h`) |
| `OYA_LOG_LEVEL` | `info` | Logging verbosity (`debug`, `info`, `warn`, or `error`) |
| `OYA_SHUTDOWN_TIMEOUT` | `10s` | Graceful shutdown timeout duration |
| `OYA_REQUEST_BODY_LIMIT` | `65536` | Maximum request body size in bytes (1 to 65536) |
| `OYA_IDEMPOTENCY_TTL` | `24h` | Expiration time for task creation idempotency keys |

Flyway migration settings (used by `make migrate`):
- `FLYWAY_URL`: `jdbc:postgresql://localhost:5432/oya?sslmode=disable`
- `FLYWAY_USER`: `postgres`
- `FLYWAY_PASSWORD`: `postgres`

HTTP server defaults: header read timeout 5 seconds, read timeout 10 seconds, write timeout 15 seconds, idle timeout 60 seconds. PostgreSQL connection pooling is managed via `pgxpool.Pool`. SIGINT and SIGTERM trigger graceful shutdown; pending requests complete before closing database connections or reaching the shutdown timeout.

## Docker

```sh
make docker-build
docker run --rm --name oya -p 8080:8080 \
  -e OYA_DATABASE_URL="postgres://postgres:postgres@host.docker.internal:5432/oya?sslmode=disable" \
  -e OYA_JWT_SECRET="production-secret-key-at-least-32-characters" \
  oya:integration
```

The application image runs as non-root UID/GID 10001 on Alpine Linux.

- `GET /healthz`: Process liveness check without querying the database (used by Docker health check via `/usr/local/bin/oya healthcheck`).
- `GET /readyz`: Readiness check that verifies PostgreSQL connection pool ping and migration state; returns 503 during shutdown.
- `GET /version`: Returns build metadata (`version`, `commit`). Set Docker build arguments `VERSION` and `COMMIT` during `docker build` to inject release metadata.

## API Examples

See [resources/api/spec.yaml](resources/api/spec.yaml) for the complete OpenAPI 3.0 contract.

### 1. Authentication

Authenticate with username and password to obtain a JWT bearer token:

```sh
curl -i -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"testuser","password":"password123"}'
```

Response:

```json
{
  "data": {
    "token": "<JWT_TOKEN>",
    "token_type": "Bearer",
    "user": {
      "public_id": "01946c10-...",
      "email": "user@example.com",
      "username": "testuser",
      "display_name": "Test User"
    }
  }
}
```

Include the token in all protected requests: `-H 'Authorization: Bearer <JWT_TOKEN>'`.

### 2. Boards

#### Create a Board

```sh
curl -i http://localhost:8080/api/v1/boards \
  -H 'Authorization: Bearer '$TOKEN \
  -H 'Content-Type: application/json' \
  -d '{"title":"Product Roadmap","description":"Q4 initiatives"}'
```

Returns `201 Created` with a `Location: /api/v1/boards/{public_id}` header and board details.

#### List Boards

```sh
curl http://localhost:8080/api/v1/boards \
  -H 'Authorization: Bearer '$TOKEN
```

#### Get Board Details

```sh
curl http://localhost:8080/api/v1/boards/BOARD_PUBLIC_ID \
  -H 'Authorization: Bearer '$TOKEN
```

#### Update a Board

```sh
curl -X PATCH http://localhost:8080/api/v1/boards/BOARD_PUBLIC_ID \
  -H 'Authorization: Bearer '$TOKEN \
  -H 'Content-Type: application/json' \
  -d '{"title":"Updated Roadmap Title"}'
```

#### Delete a Board

```sh
curl -i -X DELETE http://localhost:8080/api/v1/boards/BOARD_PUBLIC_ID \
  -H 'Authorization: Bearer '$TOKEN
```

Performs a soft delete (`deleted_at`), cascading soft deletion to all associated tasks. Returns `204 No Content`.

### 3. Tasks

#### Create a Task

Tasks must be created within an existing board by supplying `board_id`:

```sh
curl -i http://localhost:8080/api/v1/tasks \
  -H 'Authorization: Bearer '$TOKEN \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: task-create-001' \
  -d '{
    "board_id": "BOARD_PUBLIC_ID",
    "title": "Prepare release notes",
    "description": "Draft change summary for v0.3.0"
  }'
```

- Returns `201 Created`, a `Location: /api/v1/tasks/{public_id}` header, and the task payload.
- Internal database IDs are never exposed; tasks and boards use UUIDv7 `public_id`.
- The `board_id` is immutable once set.
- **Idempotency**: Retrying with the same `Idempotency-Key` and matching body replays the original response (with header `Idempotency-Replayed: true`). Retrying with the same key but different body returns `409 Conflict`.

#### List Tasks for a Board

```sh
curl 'http://localhost:8080/api/v1/boards/BOARD_PUBLIC_ID/tasks?limit=10&status=todo' \
  -H 'Authorization: Bearer '$TOKEN

# Follow forward pagination using next_cursor:
curl 'http://localhost:8080/api/v1/boards/BOARD_PUBLIC_ID/tasks?limit=10&status=todo&cursor=TOKEN' \
  -H 'Authorization: Bearer '$TOKEN
```

Tasks are sorted by `created_at DESC, public_id ASC`. Pagination is forward-only using opaque cursors; `next_cursor: null` indicates the final page.

#### Get a Task

```sh
curl http://localhost:8080/api/v1/tasks/TASK_PUBLIC_ID \
  -H 'Authorization: Bearer '$TOKEN
```

#### Update Task Status

```sh
curl -X PATCH http://localhost:8080/api/v1/tasks/TASK_PUBLIC_ID/status \
  -H 'Authorization: Bearer '$TOKEN \
  -H 'Content-Type: application/json' \
  -d '{"status":"doing","expected_version":1}'
```

Status transitions accept `todo`, `doing`, and `done`. `expected_version` is required for optimistic concurrency control; a stale version returns `409 Conflict`. Real transitions increment `version` by 1.

#### Update Task Content

```sh
curl -X PATCH http://localhost:8080/api/v1/tasks/TASK_PUBLIC_ID \
  -H 'Authorization: Bearer '$TOKEN \
  -H 'Content-Type: application/json' \
  -d '{"title":"Revised task title","description":"## Updated notes","expected_version":2}'
```

#### Delete a Task

```sh
curl -i -X DELETE http://localhost:8080/api/v1/tasks/TASK_PUBLIC_ID \
  -H 'Authorization: Bearer '$TOKEN
```

Performs a soft delete (`deleted_at`). Returns `204 No Content`.

## Database Administration & Backup

- **Flyway Migrations**: All database schema changes must be added as new migration scripts in `migrations/` following the naming convention `V<version>__<description>.sql`. Never alter migrations that have already run.
- **Backups**: Back up the PostgreSQL database using standard utilities such as `pg_dump`:
  ```sh
  pg_dump -h localhost -U postgres -d oya -F c -f oya_backup.dump
  ```
- **Restore**: Restore data to an active PostgreSQL instance:
  ```sh
  pg_restore -h localhost -U postgres -d oya --clean oya_backup.dump
  ```

## Architecture & Principles

The codebase follows the engineering principles outlined in [CONSTITUTION.md](CONSTITUTION.md) (TDD Red-Green-Refactor, KISS/YAGNI, readability, and idiomatic Go error handling):

- **Transport (`internal/transport/http`)**: Chi v5 router registering routes, JSON envelopes, security headers, panic recovery, and authentication middleware. Handlers decode input, invoke services, and serialize DTO responses.
- **Domain & Services**:
  - `internal/user`: User management, credential verification (bcrypt).
  - `internal/board`: Board domain logic, user ownership, and soft deletion.
  - `internal/task`: Task domain rules, optimistic concurrency, status transitions, and idempotency guarantees.
- **Platform**:
  - `internal/platform/auth`: JWT generation and validation (`TokenManager`).
  - `internal/platform/config`: Type-safe environment configuration loading.
  - `internal/platform/ids`: UUIDv7 generation.
  - `internal/platform/clock`: Clock interfaces allowing deterministic time in tests.
- **Persistence (`internal/persistence/postgres`)**: PostgreSQL implementation using `jackc/pgx/v5` and `pgxpool`. Database queries are defined in `queries/` and compiled to type-safe Go code using `sqlc`.
- **API Specification**: The OpenAPI contract is maintained in [resources/api/spec.yaml](resources/api/spec.yaml) and validated by tests in `internal/transport/http/openapi_test.go`.
